# W2 补充修复：SSE 在隧道下静默失效

日期：2026-11-01
发现时机：W2 验收通过后，把 Web 端挂到公网隧道给用户验收时。

## 现象

通过 cloudflared 隧道访问控制窗：

- 页面能加载，书卷列表正常
- 点选经文后，**界面毫无反应**，「未选经文」一直不消失
- `getState()` 返回的 selection 是**正确的**（`{sn:43,chapter:3,verses:{from:16,to:17}}`）
- 服务端 `/api/state` 也是正确的
- **console 零报错，零未捕获 Promise**

即：数据全对，界面永不刷新，且没有任何错误线索。

## 根因

浏览器桥接只有一个数据入口——`EventSource('/api/events')`。实测：

```
本地  http://127.0.0.1:8789/api/events  → retry: 1000 / event: state（正常）
隧道  https://<tunnel>/api/events       → 8 秒零字节（完全静默）
```

**cloudflared 免费隧道会缓冲 SSE 响应流**。连接建立成功、不报错、不断开，但事件永远不到达浏览器。

`EventSource` 在这种状态下不会触发 `error`——它认为连接是好的，只是没数据。所以应用无从感知，监听器永远等不到回调。

这类失败最危险：没有异常、没有超时、没有日志，只有"东西不动了"。

## 修复：看门狗 + 轮询降级

`src/web/bridge-client.ts`：

1. SSE 建立后启动 `sseStallMs`（默认 2500ms）看门狗
2. 期间收到**任何**事件（state/banner/scroll）就撤掉看门狗，说明通道是通的
3. 看门狗到期 → 判定 SSE 不可用 → 关闭 EventSource（避免半死连接占资源）→ 启动轮询 `GET /api/state`（默认 1000ms）
4. 两条通道都可能送 state，用 `JSON.stringify` 序列化去重，避免同一状态重复渲染

设计取舍：

- **不改服务端**：SSE 在有条件的网络里仍是最好选择（实测本地 45ms 同步）；这里只让客户端能自救
- **轮询只补 state**：`scroll`（控制窗 PgDn 驱动投影滚动）在轮询模式下失效。它属于辅助功能，静默降级比报错更合适
- **阈值 2500ms**：服务端连上即推一次 state，正常情况下远快于此，不会误判

## 验证

单元测试（新增 3 个，共 316 个全绿）：

1. SSE 迟迟无事件 → 看门狗到期 → 关闭 SSE → 轮询 → 回调收到状态
2. 轮询模式下状态未变不重复回调
3. SSE 正常收事件时不启动轮询

隧道实测（390×844 手机视口）：

| 项 | 结果 |
|---|---|
| 选经后 UI 更新 | `约翰福音 3:16-17` ✓ |
| 预览渲染 | 墨金主题经文正常 ✓ |
| 投影页内容 | 与选区一致 ✓ |
| 横向溢出 | 0 ✓ |

## 教训

**"连接成功"不等于"通道可用"。** 对长连接/流式接口，只判断建立或错误是不够的——必须验证**数据能到达**。凡是单向依赖某条流的架构，都该有超时看门狗和降级路径，否则中间层一缓冲就变成静默瘫痪。

同类风险点（本次未改，记录在案）：`SSE` 在有企业代理、CDN、负载均衡的部署环境里都可能被缓冲。
